# Status-page incidents

Incidents publish service-impact updates on a status page. Choose a status page
in **Incidents**, write a title and initial update, then post lifecycle updates
as the investigation progresses:

1. **Investigating** — the initial state for every new incident.
2. **Identified** — the cause is known.
3. **Monitoring** — a fix is in place and being observed.
4. **Resolved** — the service has recovered.

Each update is kept in the incident timeline. Incidents are scoped to the
workspace that owns their status page; a published page exposes its incidents
without exposing workspace IDs. An unpublished page's incidents remain private.
Public pages show the most recent 50 incidents.

The authenticated API provides `GET /api/v1/incidents`, `POST /api/v1/incidents`
with `status_page_id`, `title`, and `message`, and
`POST /api/v1/incidents/{id}/updates` with a lifecycle `status` and `message`.
The public endpoint is
`GET /api/v1/status-pages/slug/{slug}/incidents`.

Incident updates are currently displayed on the associated status page and do
not trigger notification-channel sends.
